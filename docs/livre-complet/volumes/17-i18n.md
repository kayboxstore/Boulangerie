# Volume 17 — Internationalisation

**Niveau de risque : 2 — Fonctionnel standard.** Quatre fichiers volumineux (~1100 lignes chacun) mais répétitifs par nature — traités selon la règle Niveau 2 du mandat (complet sur la structure et les symboles, sans citer chaque paire clé/valeur individuellement). Une vérification structurelle complète (parité des clés entre les 4 langues) a été menée par script plutôt que par lecture ligne à ligne, plus fiable pour ce type de fichier.

## 1. Ce que couvre ce chapitre

- `apps/web/src/i18n/index.ts` (33 lignes, lu intégralement)
- `apps/web/src/i18n/fr.json`, `en.json`, `ln.json`, `sw.json` (structure et parité vérifiées ; échantillon lu intégralement, le reste par vérification automatisée des clés)

## 2. Intuition

Quatre langues (Français, Lingala, Anglais, Kiswahili — section 3.8 de la spec), chacune un fichier JSON de dictionnaire, initialisées une seule fois au démarrage de l'application (`i18n/index.ts`, appelé par `main.tsx`, Volume 8). Seuls les **labels de l'interface** sont traduits — jamais les données saisies par un utilisateur (nom d'un client, motif d'une dépense...), qui restent telles quelles quelle que soit la langue d'affichage active. Cette distinction, déjà pressentie dans plusieurs chapitres sans être formalisée, est le principe organisateur de tout ce module.

## 3. `i18n/index.ts` — initialisation et repli

```ts
export const RESSOURCES = {
  FR: { translation: fr }, LN: { translation: ln }, EN: { translation: en }, SW: { translation: sw },
} as const;

i18n.use(initReactI18next).init({
  resources: RESSOURCES,
  lng: LANGUE_DEFAUT_PAR_DEFAUT, // "FR"
  fallbackLng: "FR",
  interpolation: { escapeValue: false },
});

export function appliquerLangue(langue: Langue) {
  if (i18n.language !== langue) void i18n.changeLanguage(langue);
}
```

Trois points techniques :

- **`fallbackLng: "FR"`** : toute clé absente d'une langue retombe sur sa version française plutôt que d'afficher la clé brute (`nav.dashboard` au lieu de « Tableau de bord ») — filet de sécurité pour une traduction incomplète, jamais un texte technique visible par un utilisateur final.
- **`interpolation: { escapeValue: false }`** : react-i18next échappe par défaut le HTML dans les valeurs interpolées (`{{variable}}`) — désactivé ici car React échappe déjà lui-même tout ce qu'il rend (double échappement inutile, comportement standard documenté de react-i18next avec React).
- **`appliquerLangue` est idempotent** : elle ne rappelle `changeLanguage` que si la langue demandée diffère de la langue active — évite un rechargement inutile de toutes les traductions à chaque rendu si la fonction est appelée en boucle (ex. dans un effet React mal dépendant).

## 4. Le français, langue source — Lingala et Kiswahili en « premier jet »

Un commentaire du code, confirmé par une clé `_note` présente **uniquement** dans `ln.json` et `sw.json` (absente de `fr.json`/`en.json`) :

> « PREMIER JET Lingala — NON DÉFINITIF. La terminologie métier (dette/nyongo, avance/avanse, bac, commission/komisio, clôture, seuil, etc.) doit être relue par un locuteur natif avant toute mise en production pour le personnel. Ne pas considérer ces traductions comme validées. »

C'est une déclaration honnête du projet sur l'état réel de ces deux traductions, jamais dissimulée — le livre la relaie telle quelle plutôt que de présenter les 4 langues comme équivalentes en maturité. L'anglais, en revanche, ne porte aucune réserve de ce type.

## 5. Vérification de parité — 1013 clés, exactement les mêmes

Une vérification automatisée (aplatissement récursif de chaque JSON en un ensemble de clés pointées, ex. `nav.dashboard`) donne un résultat net :

| Fichier | Nombre de clés | Écart avec `fr.json` |
|---|---:|---|
| `fr.json` | 1013 | — (référence) |
| `en.json` | 1013 | Aucun |
| `ln.json` | 1014 | `_note` uniquement (§4) |
| `sw.json` | 1014 | `_note` uniquement (§4) |

**Parité exacte confirmée** sur les 1013 clés fonctionnelles communes — aucune clé manquante ni surnuméraire dans aucune des 4 langues, seule la clé `_note` (non fonctionnelle, jamais lue par le code applicatif) distingue les deux fichiers « premier jet » des deux fichiers de référence. C'est une garantie de robustesse notable pour un projet de cette taille : un changement d'écran qui ajoute un label doit être répercuté dans les 4 fichiers pour ne pas déclencher de repli silencieux vers le français (§3) — la parité actuelle montre que cette discipline a été tenue jusqu'ici.

## 6. Organisation par namespace — un espace de noms par écran

Les 39 namespaces de premier niveau (`common`, `nav`, `login`, `profil`, `caisse`, `commandes`, `production`, `travailleurs`, `assistant`...) correspondent presque terme à terme aux écrans et modules déjà couverts chapitre par chapitre dans ce livre — `common` regroupe les libellés génériques réutilisés partout (« Enregistrer », « Annuler », « Total »...), les autres namespaces sont propres à un écran ou une famille d'écrans (ex. `bonsLivraison`, `schemaCommande`, `zonesDepot`, tous rencontrés au Volume 11z-2/11z-3). Cette correspondance directe entre structure de traduction et structure fonctionnelle de l'application est cohérente avec l'organisation du code source elle-même (Volume 7 : un fichier de route ou de page par domaine).

## 7. Langue par défaut de la boutique vs langue individuelle

Deux niveaux de préférence de langue, déjà mentionnés séparément aux Volumes 11z-4 et 11z-5 sans être mis en regard :

- **`langueDefaut`** (paramètre de la boutique, `routes/parametres.ts`, Volume 11z-4) : la langue par défaut de l'application pour tout compte n'ayant pas de préférence individuelle.
- **`Utilisateur.languePreferee`** (champ nullable sur le compte, `UtilisateurDTO`, déjà cité au Volume 11b) : `null` signifie « suivre la langue par défaut de la boutique », une valeur explicite prime sur le réglage boutique. Modifiable par chaque utilisateur depuis son profil (`ProfilPage`, `languageDefault: "Par défaut de la boutique ({{langue}})"` — clé vue à la lecture de `fr.json`, §2 illustrant l'interpolation `{{langue}}`).

`appliquerLangue` (§3) est le point d'exécution commun aux deux : que la langue effective provienne du réglage boutique ou d'une préférence individuelle, elle transite par cette même fonction pour être appliquée à l'instance i18next.

Section 3.9 (langue par défaut de l'application, modifiable individuellement) : confirmée (§7). Aucun écart.

## 9. Erreurs fréquentes et cas limites

- **Une nouvelle clé ajoutée à `fr.json` mais oubliée dans les 3 autres fichiers** : repli automatique et silencieux vers le français pour cette clé précise (`fallbackLng`) — aucune erreur visible, mais une incohérence de langue locale sur cet écran jusqu'à correction.
- **Traduction Lingala/Kiswahili utilisée en production sans relecture native** : signalé explicitement par la clé `_note`, jamais caché à qui ouvre le fichier.
- **Donnée métier confondue avec un label** : la distinction reste à la charge du développeur ajoutant un écran — rien dans le code n'empêche mécaniquement de coder en dur un texte qui aurait dû passer par `t(...)`, seule la discipline observée (vérifiée à travers tous les chapitres applicatifs de ce livre, où chaque libellé d'interface passe systématiquement par `t("...")`) le garantit en pratique.

## 10. Résumé

L'internationalisation de ce projet repose sur une structure simple (4 fichiers JSON plats, un espace de noms par écran) rendue fiable par une discipline vérifiable : parité exacte des 1013 clés fonctionnelles entre les 4 langues, un repli explicite vers le français pour toute lacune, et une transparence assumée sur la maturité inégale des traductions (le français et l'anglais validés, le lingala et le kiswahili explicitement signalés comme premiers jets). La distinction entre label d'interface et donnée métier, déjà pressentie à plusieurs reprises dans ce livre, trouve ici sa formulation complète.
